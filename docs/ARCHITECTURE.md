# Reem Application Architecture

## Overview

The Flutter client uses feature-first Clean Architecture. Each feature owns its
domain contracts, data adapters, and presentation state, while `core/` provides
cross-cutting primitives that are stable enough for every feature to share.

```text
lib/
  main.dart          Entry point: bind, bootstrap, run
  app/               MyApp + AppBootstrap (initialization, theme, locale)
  core/              Shared platform, network, result, cache, sync, state, DI
  features/          Feature modules: auth, discovery, checkout, profile, ...
  l10n/              Generated localization output
```

`app/` holds only the two files that start the application. Everything else is
either a cross-cutting primitive (`core/`) or a feature module (`features/`).
There is no top-level `app.dart` beside the `app/` directory -- that collision
is what the layout is written to avoid.

## Layer Rules

| Layer | Responsibility | May depend on | Must not depend on |
| --- | --- | --- | --- |
| Presentation | Widgets, Riverpod providers, UI state, navigation events | Domain use cases, core presentation primitives | Dio, remote data sources, data models |
| Domain | Entities, value objects, repository contracts, use cases | `core/result`, `core/domain` | Flutter, Riverpod, Dio, storage, data layer |
| Data | Remote/local data sources, DTO parsing, repository implementations | Domain contracts, core network/cache/sync | Widgets, provider state, route objects |

## Core Contracts

- `Result<T>` is the only expected success/failure boundary between repositories,
  use cases, and presentation controllers.
- `Failure` carries user-safe messages plus production metadata: error code,
  HTTP status, retryability, severity, cause, and stack trace.
- `RepositoryHandler.guard()` maps `AppException` into `Failure` and shields
  presentation code from thrown infrastructure exceptions.
- `BaseRemoteDataSource` centralizes Dio calls, error mapping, typed decoding,
  and paginated response parsing.
- `PageRequest`, `PageInfo`, and `PaginatedData<T>` define reusable pagination
  contracts for large lists and infinite scrolling.
- `PaginatedNotifier<T>` and `PaginatedState<T>` implement reusable load,
  refresh, and load-more state transitions with rebuild-friendly immutable
  state.
- `CacheStore`, `MemoryCacheStore`, `CachePolicy`, `RetryPolicy`, and
  `DataSynchronizer` provide cache-first, network-first, network-only,
  cache-only, and stale-while-revalidate strategies.

## Dependency Direction

```text
UI widget
  -> Riverpod provider/notifier
    -> use case
      -> repository contract
        <- repository implementation
          <- remote/local data sources
            <- Dio, cache, storage, connectivity
```

Dependencies point inward. Data implements domain contracts; domain never knows
which backend, database, cache, or state-management tool is being used.

## Repository Standard

Repository implementations should:

- return `Future<Result<T>>`, never throw into presentation;
- wrap remote/local work in `guard(operation: 'clear operation name')`;
- choose a cache/sync strategy explicitly for read-heavy data;
- keep mutation side effects small and deterministic;
- convert DTOs to domain entities before returning data;
- hide retry, token refresh, response-shape normalization, and storage details.

## Provider Standard

Providers should:

- expose dependencies from the narrowest useful abstraction;
- prefer `.select(...)` for UI selectors that read small state fragments;
- use `autoDispose` for route-scoped screens and keep app-wide session/cart
  state alive intentionally;
- keep controllers focused on state transitions and user intents;
- reuse `PaginatedNotifier<T>` for large lists instead of reimplementing paging.

## Import Convention

Every directive inside `lib/` uses `package:reem/...`, never a relative path.
Relative imports break the moment a file moves -- folding the widget tree into
the design system meant rewriting 102 of them by hand, which is the reason this
rule exists.

```dart
import 'package:reem/core/design_system/design_system.dart';  // yes
import '../../../../core/design_system/design_system.dart';   // no
```

Enforcement is split, because no single tool covers both directives:

- `always_use_package_imports` (analyzer) covers `import`.
- `lib-directives-must-use-package-imports` in
  `tools/architecture/check-flutter-boundaries.mjs` covers `import` **and**
  `export`. The barrels are almost entirely exports, so without this half they
  would drift back unnoticed.

`lib/l10n/app_localizations*.dart` is the one exemption. It is regenerated by
`flutter gen-l10n` with relative imports, so it is excluded from analysis and
skipped by the checker rather than edited -- any hand fix there is erased by the
next generation.

## Where Shared Code Lives

Two homes exist for code more than one feature needs, and the boundary between
them is what keeps a second widget library from growing beside the first.

| Home | Holds | Test |
| --- | --- | --- |
| `core/design_system/` | Every shared widget, token, theme, effect, and screen pattern | Would a designer name it? Then it belongs here |
| `core/shared/` | Entities, DTO models, value objects -- no UI at all | Would it survive a total visual redesign? |

`core/design_system/` is entered through its barrels, and the barrel is the
import surface: a call site that already imports `design_system.dart` must not
also import the component file directly. `unnecessary_import` is promoted to an
error precisely so that drift fails the build.

Within the design system:

- `foundation/` -- tokens, theme, motion, layout. No composite widgets.
- `components/` -- single-purpose widgets, grouped by kind (`buttons/`,
  `cards/`, `avatars/`, `inputs/`, ...).
- `patterns/` -- composites over components: page scaffolds, app chrome,
  product surfaces.
- `effects/` -- glass, blur, brand backgrounds.
- `utilities/` -- context extensions.

## Structural Checks

Rules the analyzer cannot express are enforced by three scripts. All exit
non-zero on failure, so any of them can gate CI. The design-system rules --
what feature code may say about colour, type and spacing -- live in
[DESIGN_SYSTEM.md](DESIGN_SYSTEM.md).

```bash
node tools/architecture/check-flutter-boundaries.mjs
```

Fails when a `domain/` library imports Flutter, Riverpod, Dio, `go_router`, or
a `data/`/`presentation/` sibling, and when any directive under `lib/` uses a
relative path instead of `package:reem/...`. It also prints advisory debt queues --
presentation reaching for infrastructure, debug prints, DTOs inheriting from
entities, files over 500 lines -- which are meant to be burned down gradually,
not fixed in one pass.

```bash
node tools/architecture/check-design-system.mjs
```

Fails when feature code names a raw Material colour or a hex literal,
hand-assembles a `TextStyle`, hard-codes a font size or corner radius, or
spaces itself off the 4px grid. A genuine exception is marked inline with
`// ds-ignore: <rule> -- <reason>`; the reason is mandatory.

```bash
node tools/architecture/find-unreachable-dart.mjs
```

Fails when any library under `lib/` is reachable from neither `main.dart` nor a
test. Reachability is resolved through real paths, for both `package:reem/...`
and relative URIs, and iterated to a fixed point so that a file kept alive only
by another dead file is still reported.

## Known Debt

Recorded here rather than left as a silently failing gate:

- `strict-raw-types` is off. Turning it on reports 31 bare `Map`/`List`
  signatures, nearly all in `data/` model constructors. `strict-casts` is on
  and green.
- `unawaited_futures` (12) and `avoid_slow_async_io` (2) need a decision per
  call site: each is a question about whether the caller should wait, which no
  bulk fix can answer.
- `library_private_types_in_public_api` (1) and `close_sinks` (1, in a test).

`deprecated_member_use`, `use_null_aware_elements` and
`unnecessary_underscores` were burned down with `dart fix` and are now clean.
The analyzer sits at 17 informational hits and no warnings or errors.

## Current Refactor Notes

The current codebase already had useful clean-architecture seeds: feature
folders, repository contracts, use cases, `Result<T>`, and Dio error mapping.
The main scalability risks were repeated provider wiring, thin failure models,
feature-specific pagination contracts, weak cache/offline foundations, and
connectivity code that did not match the installed `connectivity_plus` API.

The refactor introduced shared enterprise primitives without forcing a risky
rewrite of every feature at once. Discovery/search pagination now runs on the
generic core pagination state machine while preserving the public provider API
that screens already use. Future features should adopt these core contracts as
they are built or touched.

## Migration Path

1. New paginated screens should return `PaginatedData<T>` from use cases and use
   `PaginatedNotifier<T>` in presentation.
2. Existing feature-specific page entities can add a mapper like
   `toPaginatedData()` until their repository contracts are migrated.
3. Read-heavy repositories should call `DataSynchronizer.resolve()` with an
   explicit `CachePolicy`.
4. DTOs that currently extend entities should gradually move to composition and
   mapper methods when those files are already being changed.
5. Add focused tests around repository failure mapping, cache policy behavior,
   and notifier state transitions as each feature migrates.
